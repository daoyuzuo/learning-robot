QoS 观测与测试

上一节课的结论是：QoS 不兼容时不报错。这一节课解决“那怎么发现”。核心思路只有一条——不要猜，读两端实际生效的配置，再用可计数的指标验证。

第一步：读配置

ros2 topic info /scan --verbose

输出会分三块：发布者、订阅者、以及每一端声明的 QoS。你要比对的就是 publisher 的 offered 和 subscriber 的 requested。只要有一项请求比提供更严格，这条连接就不会建立——即使两边都“在运行”。

如果没有 --verbose，你只能看到“有几个发布者、几个订阅者”，看不到它们是否真的连上了。这是排查时最容易省错的一步。

第二步：确认数据在动

ros2 topic hz /scan
ros2 topic bw /scan

hz 给频率，bw 给带宽。它们证明“这条链路确实在传消息”，但不证明“订阅端处理得过来”。频率正常而队列溢出，是真实存在的组合。

第三步：设计不兼容实验

  1. 让发布端用 BEST_EFFORT，订阅端用 RELIABLE。
  2. 确认两端节点都在，ros2 node list 能看到。
  3. 用 ros2 topic info --verbose 读出 offered / requested，截图或记录。
  4. 断言：订阅端收到的消息数为 0，且没有任何错误日志。
  5. 把订阅端改成 BEST_EFFORT，重跑，断言消息数大于 0。

第 4 步是这类测试的关键：它验证的不是“能收到”，而是“不兼容时确实不连通”——这条断言才能防止回归。

把消息序号（sequence id）放进 payload，丢包率就是“收到条数 / 最大序号”的补数；不要用时间窗口去估算，那会把手写的抖动混进结论。

第四步：判定质量

可用的三个指标：丢包率（序号缺口）、端到端延迟（发送时间戳与接收时间戳之差）、deadline 违约次数（相邻两条间隔超过阈值的事件）。前两个要自己算，第三个由 DDS 的 deadline 事件直接给。

阈值必须写在测试用例里，而不是“看起来还行”。例如：延迟 P99 不超过 50 ms，deadline 违约次数为 0。
