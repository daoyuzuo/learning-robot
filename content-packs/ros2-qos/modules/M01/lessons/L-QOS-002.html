QoS 策略与兼容性

QoS 是发布/订阅之间的“服务等级合同”。它不改变消息内容，只改变这条链路在丢包、延迟、重启时的行为。默认值能覆盖大多数 demo，但一到真机就会暴露问题：传感器流被可靠传输拖慢、后加入的节点收不到历史状态、订阅端静默地一条消息都不收。

六类策略

策略约束什么常见取值默认
reliability丢了要不要重传RELIABLE / BEST_EFFORTRELIABLE
durability晚加入的订阅者能不能收到历史TRANSIENT_LOCAL / VOLATILEVOLATILE
history + depth本地队列保留多少条KEEP_LAST(n) / KEEP_ALLKEEP_LAST(10)

容易混的两对：history/depth 管数量，lifespan 管时间；deadline 管“来晚没”，liveliness 管“人还在没”。

兼容性：Request vs Offered

订阅端请求它愿意接受的最低质量，发布端提供它能给出的最高质量。只有请求的每一项都不比提供的更严格，连接才建立。

  • 发布 RELIABLE、订阅 BEST_EFFORT：兼容（订阅要求更低）。
  • 发布 BEST_EFFORT、订阅 RELIABLE：不兼容（订阅要求更高）。
  • 发布 TRANSIENT_LOCAL、订阅 VOLATILE：兼容。
  • 发布 VOLATILE、订阅 TRANSIENT_LOCAL：不兼容。

不兼容不会报错：两个节点都正常运行，只是它们之间不建立连接。日志里通常什么都没有，表现就是“订阅端一条也收不到”。这是 QoS 问题最典型的误判来源。

常用 profile

传感器数据用“best effort + 较小队列”，因为丢一帧的代价小于延迟的代价；状态类、配置类话题用“reliable + transient local”，让后启动的节点也能拿到最新状态。

from rclpy.qos import QoSProfile, ReliabilityPolicy, DurabilityPolicy

sensor_qos = QoSProfile(depth=5, reliability=ReliabilityPolicy.BEST_EFFORT)
state_qos = QoSProfile(
    depth=1,
    reliability=ReliabilityPolicy.RELIABLE,
    durability=DurabilityPolicy.TRANSIENT_LOCAL,
)
