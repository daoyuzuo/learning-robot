Flakiness、基线与趋势分析

学完你能：定位 Flakiness 的来源，建立包含版本、场景、环境和样本量的基线，并用分位数和趋势图判断异常。

本课主读：R-ISO-18646-2《ISO 18646-2:2019 服务机器人性能准则 — 第 2 部分：导航》。重点看导航试验的重复条件和指标口径，理解基线为什么必须绑定条件。

一、15% 的用例“时不时失败”

某团队的导航回归里有 15% 的用例“时不时失败”。一开始大家还会看日志，后来形成习惯：失败了就重跑，重跑通过就算过。三个月后，一个真实缺陷被这种习惯掩盖了两周：每次失败都被当作“已知的偶发问题”重跑掉，直到现场发生碰撞才被重视。

Flakiness 指同一版本、同一用例在不同运行中给出不一致结果。它会侵蚀团队对测试的信任：当真失败和假失败混在一起，大家开始习惯性重跑，缺陷就被放过了。

二、Flakiness 的代价

  • 信任成本：团队不再相信失败信号，真实缺陷被忽略。
  • 时间成本：反复重跑、排查、开会，发布周期被拉长。
  • 质量成本：不稳定用例被隔离或删除，覆盖悄悄下降。
  • 决策成本：通过率失去意义，发布评审无法判断。

Flakiness 不是“测试的小毛病”，而是质量信号系统的故障。一个经常误报的告警和没有告警一样危险。

三、常见来源

来源典型表现排查方法
时间超时太短、固定 sleep、时间戳精度不足记录耗时分布、检查超时设置
并发资源竞争、共享状态、异步回调顺序串行复跑、加锁、检查共享变量
环境场地、光照、网络、后台负载固定环境、分层复跑、记录条件

四、如何检测 Flakiness

最直接的方法是重复运行同一用例，统计通过率。建议：

  • 对关键用例至少重复 5–10 次，记录每次结果和耗时。
  • 在 CI 中保留历史通过率，按用例统计最近 30 天的失败次数。
  • 对失败用例做隔离复跑：单独跑、换环境跑、串行跑、固定种子跑。
  • 用二分法定位：逐步缩小场景、输入、并发和环境条件。
  • 记录失败时的完整日志、版本、环境和资源状态。

不要用“重跑通过”作为关闭条件。重跑只能说明问题不稳定，不能说明问题不存在。

# 从 CI 结果里统计每条用例近 30 天的失败率，并区分“偶发失败”与“真失败”
from collections import defaultdict
from datetime import datetime, timedelta, timezone

def flaky_report(runs, days=30, min_runs=10, threshold=0.10):
    cutoff = datetime.now(timezone.utc) - timedelta(days=days)
    stats = defaultdict(lambda: {"pass": 0, "fail": 0})
    for run in runs:
        if run["finished_at"] < cutoff:
            continue
        stats[run["case_id"]]["fail" if run["failed"] else "pass"] += 1

    report = []
    for case_id, s in stats.items():
        total = s["pass"] + s["fail"]
        if total < min_runs or s["fail"] == 0:
            continue
        rate = s["fail"] / total
        if rate >= threshold:
            report.append((case_id, total, round(rate, 3)))
    return sorted(report, key=lambda item: -item[2])

# 输出示例：[('nav_turn_narrow', 20, 0.15)]
# estop_recover 是 1/12 ≈ 8.3%，低于 10% 阈值被过滤——阈值先定，再谈要不要查。
# 失败率只用来排序，定位仍要靠隔离复跑与日志对比。

统计只能把“可疑用例”排到前面，不能直接给出原因。真正定位还是靠隔离复跑：单独跑、换环境跑、串行跑、固定种子跑，逐项比较差异。

五、基线是什么

基线是“在明确条件下，指标应该落在哪里”。它至少包含：版本、场景、环境、样本量、指标定义和统计口径。没有这些信息，基线只是一个数字。

字段示例
版本导航 3.4.2、模型 2026-10-18、地图 v12
场景园区 A 路线 3，含 2 个路口、1 个地下车库
环境晴天、光照 500 lux、地面干燥、无网络拥塞
样本量30 次，每次完整任务
指标任务成功率、P95 耗时、最小障碍距离
口径成功率按比例；耗时取 P95；距离取最小值

基线要随版本更新，但更新必须有依据：需求变更、缺陷修复、环境变化。基线漂移会让“通过”失去意义。

六、可视化：让波动可解释

  • 箱线图：看中位数、四分位距和离群点。适合比较多个版本或场景。
  • P95/P99 趋势：看尾部风险随时间的变化。均值平稳但 P99 上升，说明长尾在恶化。
  • 漂移曲线：看指标随运行时间、温度或里程的累积变化。
  • 热力图：看场景与指标的交叉，例如不同园区 × 不同时段的成功率。
  • 通过率时间序列：看 Flakiness 是否集中在某些版本、环境或时间段。

图表要服务于判断，而不是装饰。看到 P99 上升，应该追问：是哪些样本拉高了尾部？它们有什么共同条件？

七、实例：导航用例 15% Flakiness

检查发现结论
单独运行失败率降到 3%可能与并发或状态泄漏有关
串行运行失败率 4%并发是主要因素之一

记录耗时失败时感知耗时 P95 从 80 ms 升到 180 ms时间超时设置过紧

改进：放宽超时到覆盖 P99、隔离共享状态、固定随机种子、在下午时段增加场景样本。修复后重新建立基线，继续观察 30 天。

八、隔离与修复策略

不是所有 Flakiness 都能立刻修复。对暂时无法修复的用例，可以隔离（quarantine），但必须有规则：

  • 标记为隔离，不计入发布通过率，但保留运行和记录。
  • 指定负责人和关闭时间，例如两周内定位或删除。
  • 记录失败频率、环境和最近一次失败日志。
  • 每周评审隔离列表，避免“隔离即遗忘”。

禁止的做法：无限重跑、静默删除、把失败改成 warning。它们会让质量信号消失。

九、常见误区

  • 重跑直到通过。掩盖真实缺陷，破坏测试信任。
  • 没有基线就谈波动。不知道“正常”是什么，无法判断异常。
  • 只看均值。均值平稳但尾部恶化，用户仍然会感知。
  • 隔离后不跟踪。隔离列表变成永久垃圾场。
  • 用固定 sleep 解决时序问题。短期有效，长期让测试更慢更脆。
  • 不记录环境。无法复现，也无法解释差异。

十、检查清单

  • 是否统计了用例的历史通过率和失败频率？
  • 是否检查了时间、并发、环境、随机性、外部依赖和状态泄漏？
  • 基线是否包含版本、场景、环境、样本量和口径？
  • 是否使用箱线图、分位数、漂移曲线或热力图分析？
  • 隔离用例是否有负责人、关闭时间和每周评审？
  • 是否禁止“重跑直到通过”作为关闭条件？

十一、Flakiness 排查决策树

面对一个不稳定用例，可以按下面的顺序排查，从最便宜、最可能的原因开始：

步骤动作如果结果指向下一步
1单独运行 10 次仍失败问题在用例或被测系统本身，不是并发
2串行运行 10 次失败率下降并发或共享状态问题
3固定随机种子失败率下降随机性或采样问题
4固定环境（光照、网络、负载）失败率下降环境差异问题
5检查耗时与超时失败时耗时接近阈值超时设置过紧或性能退化
6检查资源（内存、磁盘、连接）长时间运行后失败资源泄漏或耗尽
7检查外部依赖外部服务异常时失败打桩、重试或降级

这个顺序的原则是：先排除“用例本身不稳定”，再排除“并发/状态”，最后才怀疑“环境/外部依赖”。很多团队一上来就归因于环境，结果掩盖了真正的代码缺陷。

十二、评审与面试追问

  • 问：Flakiness 和真实缺陷怎么区分？答：先看是否与随机性/环境相关；如果同一条件反复出现，或失败集中在特定场景，更可能是真实缺陷。
  • 问：重跑通过能关闭缺陷吗？答：不能。重跑只能说明不稳定，不能说明问题不存在；必须找到原因或记录隔离计划。
  • 问：基线多久更新一次？答：版本、场景、环境或需求发生实质变化时更新；至少每个发布周期复核，保留变更理由。
  • 问：为什么用 P95/P99 而不是均值？答：均值掩盖长尾，尾部延迟和失败率更影响用户体验和安全。
  • 问：隔离用例应该保留多久？答：设定明确期限（例如两周），到期必须修复、删除或升级为风险接受；不能无限期隔离。

十三、Flakiness 治理的组织机制

Flakiness 不是靠个人排查就能解决的，需要组织机制：每周固定时间评审不稳定用例列表；为隔离用例设定负责人和期限；把 Flakiness 纳入测试健康度指标；对“重跑通过”设置审批或记录要求。

还要区分“测试不稳定”和“系统不稳定”。如果同一个用例在真实环境中也偶发失败，它可能不是测试问题，而是系统缺陷。把这类用例当作噪声重跑，会掩盖真正的质量问题。判断方法是看失败是否只在测试环境出现，以及是否有现场对应现象。

基线也不是一次性的。每次版本、场景或环境发生实质变化，都要重新采样并更新基线；更新时记录变更理由和确认人。没有更新的基线，会让团队用旧标准判断新系统，最后要么误报，要么漏报。隔离列表也要公开可见，让开发和运维知道哪些用例暂时不可信，避免有人把隔离当成“测试已经通过”。隔离不是删除，必须有替代覆盖或风险接受，否则覆盖会悄悄下降。每周评审要记录结论，并更新隔离列表，直到关闭，并留档备查可查。

十四、延伸思考

  • 大量用例同时变得不稳定，先查什么？优先查共享环境、资源耗尽、测试顺序和外部依赖。
  • 隔离用例导致覆盖率下降怎么办？补替代覆盖或明确风险接受，不能把隔离当成删除。
  • 如何向管理层解释 Flakiness 的成本？用重跑时间、误报率、漏检风险和发布延迟量化。

常见误区：重跑通过就可以关闭不稳定用例。重跑通过只说明这次没触发，没找到来源就关，下次还会失败。

小结

Flakiness 是质量信号系统的故障，不是测试的小毛病。先统计失败频率，再按时间、并发、环境、随机性、外部依赖和状态泄漏逐项排查；建立包含版本、场景、环境和样本量的基线；用箱线图、分位数和趋势图解释波动；对暂时无法修复的用例执行有期限的隔离。最重要的是，不要把“重跑通过”当成问题解决。
