标准映射与合规证据

本课面向机器人测试负责人与合规工程师：把 ISO/IEC 标准条款翻译成可执行的测试活动，并让每一条“已满足”的声明背后都有可复现、可追溯的证据。课程围绕两条主线展开——标准映射（条款 → 安全功能 → 实现 → 测试 → 证据）与实验设计与统计推断（用有限样本支撑“满足限值”的结论）。

一、标准体系的三层结构与映射起点

机器人功能安全标准通常呈 A/B/C 三层金字塔：A 类给出通用安全原则与风险评估方法论（ISO 12100 / GB/T 15706）；B 类给出通用安全要求，B1 为安全控制系统（ISO 13849-1、IEC 62061，其源头是 IEC 61508），B2 为安全装置（急停 ISO 13850、联锁 ISO 14119 等）；C 类为产品专用要求（ISO 10218-1/-2、ISO/TS 15066、ISO 13482、ISO 3691-4 等）。C 类优先：当 C 类与 A/B 类冲突时按 C 类执行。

映射的第一步不是写测试用例，而是确定适用框架。适用性由预期用途、移动能力、人类可及性、是否使用 AI、运行环境与目标市场共同决定；没有任何单一标准能覆盖通用机器人系统，因此需要一份“标准清单 + 版本 + 条款”的适用性声明。

提示：标准修订会改变验收口径。证据若回答的是被取代的旧版本，在审核方眼中等同于没有证据。映射表必须记录每条证据对应的标准版本。

二、从条款到测试：合规矩阵

合规矩阵是标准映射的核心工件，一行一个条款，列至少包含：标准与版本、条款号、主题、实现位置（代码路径或设计项）、验证方式（测试/分析/检查/评审）、证据工件、责任人、状态。工程实践中常见的写法如下表（示例取自公开的机器人合规矩阵）：

标准条款主题实现验证/证据
ISO 10218-1§5.4.2保护性停止watchdog 触发路径watchdog 单元测试
ISO 10218-2§5.10协作运行接近速度降额接近速度测试
ISO/TS 15066§5.5.5功率与力限制碰撞力模型场景覆盖 + 力测量
ISO/TS 15066§5.5.4速度与分离监控监控检查监控一致性测试
IEC 61508-3§7.4软件安全生命周期形式化模型形式化证明

注意矩阵中“验证方式”一栏可以写“—”，表示该条款由流程或外部 CI 满足而非树内测试。这类条目必须额外附上流程证据（评审记录、CI 报告、供应商声明），否则就是隐性缺口。

映射时还要处理共享条款：同一份测试报告可能被同时引用到两个标准的重叠要求上，必须逐条确认它真的覆盖了每一条，而不是“一份报告记两次账”。

三、合规证据缺口：工作做了，但证明不了

合规证据缺口（compliance evidence gap）指工程工作确实完成了，但证明它的材料分散在文档、表格、测试工具、PLM 与供应商 PDF 中，且缺少机器可读的关联。典型成因有四类：

  • 链条断裂：危害、控制它的需求、实现该需求的安全功能、所需性能等级、验证方法、结果，是六个互不关联的工件。
  • 版本歧义：审核中最贵的问题往往是“这次测试跑的是哪一版设计”。
  • 责任分散：OEM、系统集成商、部件与安全装置供应商、外包工程各持一部分证据。
  • 重建文化：把技术文件当成项目末期的一次性组装工作。

与之对应的做法是“为证据而设计”（design for evidence）：在项目开始前定义证据模型（技术文件应包含什么、对应哪一条款、谁负责），把可追溯性当作活的关系而非期末交付物，对一致性声明所依赖的需求/风险评估/验证结果做显式基线，并在工作发生处记录推理与批准。

可验证凭据（verifiable credential）思路把证据做成可离线复核的签名工件，例如机器人身份、模型来源、物理能力范围、安全事件账本、带运动摘要的心跳、感知来源。要特别注意每类凭据“不能证明什么”：物理能力范围凭据只能证明限值由谁设定，不能证明执行机构在物理上遵守了它；安全事件账本只能证明已记录条目未被篡改或删除，不能证明所有真实事件都被记录。把“不能证明什么”写进证据说明，是避免过度声明（over-claiming）的关键。

四、用实验设计与统计推断支撑“满足限值”

合规结论常常是统计结论：碰撞力是否低于身体部位限值、停机时间是否满足性能等级、监控偏差是否在允许带内。这里需要实验设计与统计推断的基本纪律：

  • 先定义判定规则：限值、置信水平、样本量、失败判据，在采集数据前写定，避免事后挑选。
  • 区分随机与系统不确定度：比较“观测值”与“密封参考值”时，可分辨的最小偏差由两者不共有的那部分系统测量不确定度决定，增加平均次数无法消除它，只能靠校准制度约束。
  • 警惕启动瞬态：只用一次启动瞬态期间的调试周期建立参考包络，会把包络不必要地放宽（量级约为 D/√n），从而让带检查失效——而且失效是静默的：监控看起来在运行，记录里全是合规条目。
  • 区分“没有证据”与“证据表明没有”：基于假设参数的验证只有证据的外表而没有实质，这正是证据规范要防止的失效模式。

把统计结论写进合规矩阵时，证据工件应包含原始数据、分析脚本、判定规则与结论四部分，缺一不可。

五、规划证据补齐路径

识别缺口之后，按“阻塞下游工作量”排序补齐：先补会阻塞多项后续活动的缺口（如基线缺失、版本不明），再补单点缺口。补齐路径通常有三种：补做测试（成本最高、周期最长）、改用分析或检查（需确认认证基础接受该方法）、引用供应商或第三方证据（需确认版本与配置一致）。每条路径都要在矩阵中留下决策记录。
