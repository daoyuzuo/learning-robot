一、换了制动器，问题两周后又回来

某机器人出现“急停触发后仍移动约 10 cm”的问题。团队第一次分析后更换了制动器，问题消失了两周，然后又出现。第二次分析发现，制动器本身没有问题，真正原因是急停信号在控制链路中被一个状态机过滤了 80 ms，而制动器响应时间刚好被这段延迟放大。更换制动器只是改变了边界条件，没有触及根因。

根因分析不是找一个“背锅的人”，而是找到可改变、可验证的系统原因。

二、三个层次：直接原因、根因、促成因素

  • 直接原因：直接触发失效的环节。例如“制动器延迟 120 ms”。
  • 根因：导致直接原因存在的系统性问题。例如“急停信号在状态机中被过滤，且没有超时告警”。
  • 促成因素：让根因更容易产生后果的条件。例如“负载偏重”“地面湿滑”“维护后未复测”。

只修直接原因，问题会以另一种形式回来；只修根因，不处理促成因素，风险仍然存在。完整的分析要同时覆盖三层。

三、四种方法怎么选

方法强项局限适用场景
5Why快速、低成本、易沟通假设单一因果链，容易停在表面单点、线性、原因较明确的问题
鱼骨图覆盖人、机、料、法、环、测多维度不直接给出验证顺序团队头脑风暴、原因不明的问题
8D团队协作、遏制、纠正、预防闭环流程重，适合重要问题客户投诉、重复发生、跨团队问题
FTA顶事件演绎、组合失效、可量化需要较多系统知识安全相关、多因素组合失效

实际项目里经常组合使用：先用鱼骨图展开可能原因，再用 5Why 深挖其中几条，最后用 FTA 验证关键组合。8D 则适合需要跨团队闭环和客户沟通的场景。

四、5Why：快，但要防止线性化

5Why 的基本做法是连续追问“为什么”，直到找到可改变的系统原因。以“急停后仍移动”为例：

  1. 为什么仍移动？因为制动器在急停后 120 ms 才完全抱死。
  2. 为什么需要 120 ms？因为急停信号进入状态机后被过滤了 80 ms。
  3. 为什么被过滤？因为状态机把急停当作普通事件，按周期处理。
  4. 为什么按普通事件处理？因为设计时没有区分安全信号和普通信号。
  5. 为什么没有区分？因为安全需求没有进入软件架构评审。

这条链已经触及根因，但 5Why 的风险是“只追一条线”。如果同时存在制动器磨损、负载超标、地面湿滑等促成因素，单线追问会漏掉它们。因此 5Why 适合作为起点，不适合作为唯一方法。

五、鱼骨图与 FTA

鱼骨图常用“人、机、料、法、环、测”六类展开。机器人问题可以这样分类：人（操作、示教、维护）、机（机械结构、执行器、传感器）、料（负载、工件、地面、地图）、法（流程、参数、标定、测试方法）、环（光照、温度、湿度、网络、人流）、测（传感器测量、日志、监控、判定标准）。

鱼骨图的价值是防止团队过早收敛到某一个原因。展开后要给每条可能原因标注验证方法和优先级，否则只是一张装饰图。

FTA 从“顶事件”出发，用与门、或门把失效拆成底层事件。例如顶事件“急停后仍移动”，可以拆成：制动延迟超标 OR 急停信号丢失 OR 控制指令未撤销 OR 机械惯性超出预期。每个底层事件再继续拆，直到可以验证或可以接受。FTA 适合安全相关、组合失效的场景，因为它能显式表达“多个条件同时满足才失效”。

六、假设驱动：让每条原因可验证

假设预测验证方法证据
急停信号被状态机过滤 80 ms日志中急停事件到制动指令有固定延迟对齐时间戳、查看状态机日志延迟分布、代码路径
制动器响应慢更换制动器后延迟下降台架测制动曲线制动时间对比
负载超出预期负载增加时移动距离变长变负载复测距离-负载曲线
地面摩擦不足湿滑地面移动距离变长不同地面复测摩擦系数与距离
控制指令未撤销急停后仍收到速度指令抓取 /cmd_vel 日志指令时间序列

每条假设都要有“如果成立，应该看到什么”。如果验证结果不符合预测，就要修正假设，而不是强行解释。

# 假设驱动的最小工具：把日志切成事件，量出急停→制动指令的延迟分布
import statistics

def estop_latency_ms(events, clock_skew_ms=0):
    """events: [(t_ms, name)]，按时间升序；返回每次急停到首个制动指令的延迟。"""
    latencies, pending = [], None
    for t, name in events:
        if name == "estop_asserted":
            pending = t
        elif name == "brake_command" and pending is not None:
            latencies.append(t - pending - clock_skew_ms)
            pending = None
    return latencies

samples = estop_latency_ms([
    (1000, "estop_asserted"), (1090, "brake_command"),
    (3000, "estop_asserted"), (3082, "brake_command"),
    (5200, "estop_asserted"), (5286, "brake_command"),
])
print(len(samples), statistics.mean(samples), max(samples))  # 3 86 90

# 预测“状态机固定过滤 80 ms”时，延迟应集中在 80±5 ms；
# 若出现 200 ms 的离群值，说明还有第二个原因，不能只修状态机。

这段脚本只有十几行，但它把“我觉得是状态机”变成了可证伪的预测。假设驱动分析的产出不是结论，而是“下一次该看哪条日志”。

七、纠正与预防

纠正措施针对已经确认的原因，例如修改状态机、给安全信号加独立通道、增加超时告警。预防措施针对同类原因再次发生的条件，例如把安全信号纳入架构评审、增加安全功能测试用例、在门禁里加入急停链路验证。

措施是否有效，要用证据验证：修改后复测延迟分布、注入急停信号验证、检查同类模块是否也存在过滤逻辑。没有验证的措施只是“希望它有用”。

八、常见误区

  • 把直接原因当根因。更换零件可能让问题暂时消失，但没有改变系统性条件。
  • 5Why 只追一条线。漏掉并行的促成因素。
  • 鱼骨图不验证。列了一堆可能原因，没有一条有证据。
  • FTA 没有边界。顶事件定义太宽，树无限展开。
  • 纠正措施没有验证。改完不复测，不知道是否真的有效。
  • 结论是“操作员失误”。通常说明防错设计或培训还有改进空间。

九、检查清单

  • 是否区分了直接原因、根因和促成因素？
  • 方法选择是否匹配问题类型？
  • 每条原因是否有可验证的假设和证据？
  • 是否检查了并行的促成因素？
  • 纠正措施和预防措施是否分别定义？
  • 措施是否经过复测或验证？
  • 同类模块是否做了横向排查？

十、FTA 示例：急停后仍移动

把顶事件“急停后仍移动超过 10 cm”向下拆，可以得到一棵简化的故障树：

层级事件逻辑验证方法
顶事件急停后仍移动超限OR实机测试、日志分析
中间事件 1制动延迟超标OR制动曲线、台架测试
底事件 1.1制动器磨损—维护记录、制动力测试
底事件 1.2负载超出设计—负载称重、变负载复测
底事件 1.3地面摩擦不足—不同地面复测
中间事件 2急停信号未及时到达OR信号时间戳、链路检查
底事件 2.1状态机过滤—代码路径、日志
底事件 2.2通信延迟/丢包—通信注入、抓包
中间事件 3控制指令未撤销OR指令日志
底事件 3.1缓存指令继续下发—抓取 /cmd_vel
底事件 3.2控制器复位未完成—复位时序、状态机

FTA 的价值是让你看到“多个原因同时存在”的路径。例如“制动器磨损 AND 负载超预期 AND 地面湿滑”才导致超限；单独修制动器可能让问题暂时消失，但另外两个条件仍在。最小割集列出“哪些底事件组合一旦同时发生就会导致顶事件”，对每个最小割集设计验证用例，比按模块平均分配测试更有针对性。

十一、评审与面试追问

  • 问：5Why 和 FTA 最大的区别？答：5Why 是线性追问，FTA 是树状演绎，能表达组合失效和并行原因。
  • 问：根因一定要唯一吗？答：不一定。复杂问题常有多个促成因素，关键是找到可改变、可验证的系统原因。
  • 问：怎么避免“猜一个原因就修”？答：把每条原因写成假设，给出预测和验证方法，用证据确认或否定。
  • 问：纠正和预防怎么区分？答：纠正针对已发生的问题，预防针对同类问题再次发生的条件；两者都要有验证。
  • 问：根因分析什么时候停？答：当原因可改变、可验证，且继续追问不会带来新的可执行措施时停止；不是必须问满五次。

十二、根因分析会议怎么开

会议的目标不是当场得出结论，而是把假设和验证计划分下去。建议流程：先用 10 分钟对齐现象和影响；再用 15 分钟展开候选原因；然后逐条写假设、预测和验证方法；最后明确负责人和截止时间。会议结束时应有一张假设表，而不是一句“可能是软件问题”。

参会者要包含能提供证据的人：测试、研发、运维、现场支持。没有现场证据的会议很容易变成经验之争。对安全相关缺陷，还要有安全负责人参与，确认是否需要暂停发布或限制使用。会议记录要保留假设和结论的对应关系，下一次复盘可以直接对照；建议用表格记录假设、验证方法和结果，并指定谁在什么时候关闭假设。没有对应关系的记录，只会变成一份无法复用的纪要。假设表要随证据更新，结论才能可信。

会议结束后还要做横向排查：同一个状态机、同一类传感器、同一个通信模块是否也存在相同逻辑。只修一个现场问题，不做横向排查，等于把同类风险留在其他产品线里。

根因分析的输出也要进入缺陷单、回归集和设计评审清单。否则分析结论只停留在复盘文档里，下一版仍然会用同样的架构犯同样的错误。根因分析不是一次性的会议，而是一条从现象到假设、证据、措施、验证的闭环记录。

常见误区：更换制动器让问题暂时消失，就等于找到根因。没有假设验证与预防措施，同一个缺陷会换个部件再来一次。

小结

根因分析的目标不是找到一个听起来合理的原因，而是找到一个可改变、可验证的系统原因，并用证据证明它。5Why 快但容易线性，鱼骨图广但需要验证，8D 适合跨团队闭环，FTA 适合组合失效。无论用哪种方法，都要把原因写成假设，用预测和证据来确认，再用纠正和预防措施把问题关掉。
